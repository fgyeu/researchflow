## 实验一：工具结果缓存的收益

### 问题

加了缓存到底有用吗？—— 必须有数字，否则就是"我觉得有用"。

### 设计

四个场景，每个跑 6 个研究任务：

| 场景 | 缓存 | 问题 | 用途 |
|---|---|---|---|
| A | 关 | 全不同 | 基线（每次都要真调外部） |
| B | 开 | 全不同 | **对照组**：证明缓存不会凭空命中 |
| C | 关 | 重复 | 基线（重复但不缓存） |
| D | 开 | 重复 | 缓存真正生效的场景 |

B 这一组很关键。如果只测 D 得到 100% 命中率，那只说明"我一直在问同一个问题"，
不能证明缓存设计的价值。B 组的存在让结论可信。

### 结果

| 场景 | 工具调用 | 真实外部请求 | 命中率 |
|---|---:|---:|---:|
| A 缓存关 + 全不同 | 12 | **12** | 0% |
| B 缓存开 + 全不同 | 12 | 7 | 41.7% |
| C 缓存关 + 重复 | 12 | **12** | 0% |
| D 缓存开 + 重复 | 12 | **3** | 75.0% |

**A → D：外部请求从 12 次降到 3 次，减少 75%。**

### 结论与解读

- 重复场景下，缓存把外部调用砍掉了四分之三。这是可以直接换算成成本和时间收益的。
- B 组 41.7% 的命中率来自 `read_url` 读的是同一份文档（不同研究问题常常参考同一份资料），
  这是真实世界里常见的模式，不是实验设计瑕疵。
- **缓存不缓存失败结果**：失败往往是瞬时的，缓存 1 小时等于把 3 秒的故障放大成 1 小时。

### 复现

```bash
MOCK_LLM=1 python scripts/experiment_cache.py --runs 6
```

## 实验二：可靠性

### 2.1 并发吞吐

**设计**：8 个任务，工具每次调用模拟 0.15s 延迟（代表网络等待），
比较并发上限 1 / 2 / 4 的总耗时。

没有延迟就测不出并发价值 —— 纯 CPU 计算几乎瞬间完成，串行并行差不多。

| 并发上限 | 总耗时 | 加速比 | 成功 |
|---:|---:|---:|---:|
| 1 | 40.15s | 1.00x | 8/8 |
| 2 | 20.16s | 1.99x | 8/8 |
| 4 | 10.13s | **3.97x** | 8/8 |

**结论**：接近线性加速。这符合预期 —— 任务主要是 I/O 等待（等模型、等网络），
并发能把等待时间重叠起来。这也证明了 `asyncio.to_thread` 的设计是对的：
同步阻塞的 Agent 被丢到线程池，事件循环不被堵住。

### 2.2 故障注入与重试

**这个实验我推翻重做了两次，过程本身比结论更值得记。**

**第一版**统计任务成功率 → 注入 40% 失败后任务仍 100% 成功。
原因：Agent 有降级交付，工具挂了它照样写报告，状态是 `succeeded`。
**任务成功率被污染了。**

**第二版**改统计工具调用失败率 → 两组都是 30% 左右，看不出差别。
原因：用"每 N 次调用失败一次"来模拟故障，失败率恒定在 33%，
重试只是增加了总调用数（20→29），失败次数也按比例涨（6→9）。
**故障模型选错了，重试永远看不出效果。**

**第三版（最终）**：模拟真实的"瞬时故障"——
每个工具第 1 次调用失败，之后成功。这才是重试真正有用的场景。

| 配置 | 任务完成 | **拿到真实数据** | 调用次数 |
|---|---:|---:|---:|
| 关闭重试 | 100% | **90%** | 20 |
| 开启重试(2次) | 100% | **100%** | 22 |

**结论**：

- 看"任务完成率"这栏，两组都是 100%，**看不出任何差别**。
- 看"拿到真实数据"这栏，重试把 90% 提升到 100%。
- 这个差距正是"任务成功"这个指标会**掩盖问题**的证据。

面试时这个例子可以直接讲：*"我发现系统的成功率和数据质量是两回事。
工具挂了 Agent 仍会降级交付，任务状态照样是成功。所以我加了'是否拿到真实数据'
作为独立指标，才测出重试的实际价值。"*

### 2.3 崩溃恢复

**设计**：造 5 个任务并让 Worker 领走，然后让租约立即过期（等价于 Worker 崩溃），
再触发恢复流程。

| 指标 | 结果 |
|---|---|
| 制造的中断任务 | 5 |
| 扫描到的孤儿 | 5 |
| 触发恢复 | 5 |
| **最终成功** | **5/5 (100%)** |
| 平均尝试次数 | 2.0 |
| 恢复后剩余孤儿 | 0 |

**结论**：任务在崩溃后能全部被捡回并跑完。
平均尝试 2 次符合预期（第 1 次崩溃、第 2 次成功）。

另外还做了真实进程级验证（不在这个脚本里）：
强杀 uvicorn 进程 → 数据库里任务卡在 `running` → 重启 → 自动恢复到 `succeeded`、
`attempts=2`。这验证的是**真实崩溃**，不是模拟状态。

### 复现

```bash
MOCK_LLM=1 python scripts/experiment_reliability.py --tasks 10
```

## 这些数据的边界（必须诚实说明）

1. **用 Mock 模型 + 桩化工具**。测的是系统的调度、缓存、恢复行为，
   不是模型的智能程度。这部分与真实模型无关，所以结论有效。
2. **不在真实网络下**。真实网络会有更多抖动，数据会更难看。
   这也是为什么故障注入要单独做 —— 真实故障不可控、不可复现。
3. **单机 SQLite**。换成 PostgreSQL + 多 Worker 后，锁竞争会成为新变量，
   这批数据不能直接套用。
4. **样本量小**（每场景 6~10 个任务）。够看出趋势，不够做统计显著性检验。
   如果要写进正式论文级别的东西，需要放大到几百次并报告置信区间。

**面试时说清这些边界，比吹大数字更加分。**
